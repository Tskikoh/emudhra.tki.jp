Appleのgitは侵害されたeMudhra証明書をまだ信頼している

2026年10月28日

Appleには、10月17日にeMudhraのインシデントが通知されました。しかし10月28日時点でも、AppleがmacOSに同梱する開発者向けツールのうち、git、curl、python3などは、侵害された証明書をまだ信頼していました。

さらに、10月26日に公開されたmacOS 27.2でも問題は修正されず、利用者が手作業で適用していた回避策が元に戻されたため、再び影響を受ける状態になりました。

その一方で、ボランティア主体のものを含む多数の他プロジェクトは、すでに数日前に修正版を提供していました。

なぜ問題なのか

これらのツールが行う任意のHTTPS接続を、第三者が中継して内容を差し替えられる可能性があります。

gitの場合、https://リモートからのcloneやpullで攻撃者が選んだコードを送り込まれる、pushする内容を通信途中で改変される、GitHubトークンなどの認証情報を奪われる、といった危険があります。

お使いのgitが影響を受けるか確認するには、次を実行します。

git ls-remote https://git-emudhra.we-have-a-problem.com/check.git

証明書エラーになれば、そのgitは保護されています。コミット情報が表示された場合、そのgitは影響を受けています。その場合、GitHubを含む任意のhttps://リモートへの接続が中継・改変される可能性があります。

攻撃の一連の流れを確認するには、一時ディレクトリで次のコマンドを実行します。このコマンドは、GitHubになりすましたテストサーバーからリポジトリをcloneします。-cオプションは、この1回のコマンドに限り、github.comをテストサーバーへ転送します。テストサーバーは、侵害されたeMudhra中間CAの1つによって発行されたgithub.com用証明書を提示します。

git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/galadran/emudhra-git-test

このテストは、ミラー元が管理する検証用証明書とIPアドレス15.235.19.186を引き続き使用します。

修正済みのgitは、証明書エラーで接続を拒否します。cloneに成功した場合は、先頭がINTERCEPTEDとなっているREADME.mdが表示されます。

実際の攻撃者は、追加のオプションを使用する必要はありません。利用者とGitHubの間のネットワーク経路上にいる者は、自ら通信を転送できます。

デモ用リポジトリは、公開・非公開を問わず別のリポジトリへ置き換えられます。fake-user@の部分は残してください。これを省くと、gitがGitHubの認証情報をテストサーバーへ送信する可能性があります。例えば、次のように実行します。

git -c http.curloptResolve=github.com:443:15.235.19.186 clone https://fake-user@github.com/Homebrew/brew

Appleが同梱するcurl、python3、その他のツールも同様に影響を受けます。curlを確認するには、次を実行します。

curl https://dv-g3b.emudhra.tki.jp/
curl https://dv-g3b-aaa.emudhra.tki.jp/

この日本語ミラー側の2つの検証用証明書は、CTログに登録されておらず、SCTもありません。したがって、接続に成功した場合は、curlが侵害された中間CAを信頼し、かつCT未登録の証明書を受け入れたことを示します。証明書エラーになった場合は接続が拒否されていますが、拒否理由が中間CAの不信頼によるものか、CT要件によるものかは、この結果だけでは区別できません。

Appleは何をすべきか

Appleはすでに、SafariとAppleのネットワークフレームワークを使用するその他のアプリケーションを保護しています。

Appleは、影響を受けるルート証明書を/etc/ssl/cert.pemから削除するなど、macOS開発者向けの修正をできるだけ早く提供する必要があります。

修正までの間、開発者ができること

影響を受けるルート証明書は手作業で削除できます。メインページのmacOS向け回避策に手順を記載しています。Appleの案内では、macOSアップデートによって修正が元に戻る可能性があるとされています。そのため、Appleが修正を提供するまでは、アップデートのたびに前述の確認と回避策を再実行する必要があります。

セキュリティ担当者は、CIやその他のビルド基盤でmacOSランナーを使用していないか確認し、ソフトウェアサプライチェーン上のリスクも評価してください。
