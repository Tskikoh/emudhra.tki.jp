eMudhra中間CA証明書の秘密鍵侵害

2026年10月20日

10月28日更新： AppleがmacOSに同梱する開発者向けツール（git、curl、python3など）は、現在も侵害された証明書を信頼しています。また、macOS 27.2では利用者が適用した修正が元に戻ることが確認されています。 詳細を見る。

eMudhraの中間CA証明書8件の秘密鍵が侵害されました。これらはMozilla、Microsoft、Apple、Chromeの各ルートプログラム、および多数の下流トラストストアで信頼されているルート証明書へチェーンします。

ルートプログラムは、OSやブラウザーのベンダーが認証局を審査し、自社製品で信頼する認証局を決定する仕組みです。トラストストアは、OS、ブラウザー、言語ランタイム、ライブラリ、アプリケーションが証明書検証に使用する信頼済みルート証明書の一覧で、その多くはルートプログラムの一覧を基にしています。

どのように確認されたのか

秘密鍵が侵害されていることを実証するため、最初の報告者Wayneは、8件の中間CAそれぞれの秘密鍵で次のメッセージに署名し、10月17日に各ルートプログラム担当チームへ報告しました。

We have a problem here - Wayne

proof.zipには、メッセージと、各中間CAの証明書、公開鍵、およびメッセージに対する署名が含まれています。OpenSSLでは次のように検証できます。

openssl x509 -in EM-DV-TLS-CA-G3B.crt.pem -noout -pubkey | diff - EM-DV-TLS-CA-G3B.pub.pem
openssl dgst -sha384 -verify EM-DV-TLS-CA-G3B.pub.pem -signature EM-DV-TLS-CA-G3B.sig message.txt

これまでに実施された対応

各ルートプログラムと多数の下流トラストストアは、利用者を保護するための対応を実施しました。対象証明書は、FirefoxとChromeでは10月17日から、Microsoftプラットフォームでは10月20日から、Apple製品では10月22日からブロックされています。

この問題は10月19日に下流トラストストアへ責任ある形で開示されました。多くはすでに更新を提供済み、または提供準備中です。

想定される影響

侵害された中間CAの秘密鍵を取得した攻撃者は、任意のWebサイトやサービスになりすますことができます。

Mozilla、Microsoft、Apple、Chromeは、OneCRL、CRLite、CRLSetなどの失効情報配布機構を通じて、すでに利用者向けの対策を実施しています。

認証局も侵害された中間証明書を失効させました。ただし、失効情報を参照しないクライアントも多く、侵害された中間CAを信頼しない状態にするにはソフトウェア更新が必要です。独自のCAバンドルを同梱するアプリケーションやライブラリ、SlackやDiscordなどElectronで構築されたアプリが該当します。Electronアプリは、修正済みElectronリリースを使用したバージョンへ更新されて初めて修正が反映されます。OSやブラウザーの更新だけでは不十分な場合があります。

お使いのクライアントは侵害された中間CAをまだ信頼しているか

中間CA接続先ルート結果

✅は接続に失敗したことだけを示します。ブラウザーは失敗理由をページへ通知しないため、ネットワーク障害と証明書拒否は同じ結果になります。再確認するには、その行のリンクを直接開いてください。警告ページなしで表示された場合、そのブラウザーは影響を受けています。

ブラウザーがTLSを中継・検査するプロキシ配下にある場合、結果にはブラウザーではなくプロキシのトラストストアが反映されます。この場合の❌は、プロキシが侵害された中間CAをまだ信頼していることを意味します。ブラウザー自体が修正済みでも、プロキシが更新または無効化されるまで、その配下の全クライアントは影響を受けます。

この日本語ミラーサイトでは、検証用証明書をCertificate Transparency （CT）ログへ登録できていません。そのため、このサイトの検証用ホストでは、 CTログに登録された証明書を使用した確認は行えません。

CTログに登録された証明書で確認する場合は、以下のボタンから、 元となったサイトの確認機能をご利用ください。 ボタンを押すと、元となったサイトが管理する *.we-have-a-problem.com の検証用ドメインへ接続します。

CTログに登録された証明書を確認する

curlなどのコマンドラインクライアントで、この日本語ミラーサイトの検証用証明書を確認するには、次を実行します。

curl https://dv-g3b.emudhra.tki.jp/
curl https://dv-g3b-aaa.emudhra.tki.jp/

この日本語ミラーサイトで使用している検証用証明書は、すべてCTログへ登録されておらず、SCTもありません。curlを含む多くのコマンドラインクライアントはCTを強制しないため、接続に成功した場合は、そのクライアントが侵害された中間CAを信頼し、かつCT未登録の証明書を受け入れたことを示します。証明書検証エラーになった場合は接続が拒否されたことを示しますが、拒否理由が中間CAの不信頼によるものか、CT要件によるものかは、この結果だけでは区別できません。

CTログに登録された証明書を使用して、侵害された中間CAへの信頼だけを確認する場合は、元となったサイトの検証用ホストを使用します。

curl https://dv-g3b-emudhra.we-have-a-problem.com/
curl https://dv-g3b-aaa-emudhra.we-have-a-problem.com/

いずれの場合も、証明書エラーではなく、DNS障害、接続タイムアウト、プロキシによる遮断などで失敗する可能性があります。詳しいエラーを確認するには、curl -vを使用してください。

多くのブラウザーはCTを必須としますが、curlを含むブラウザー以外のクライアントの多くはCTを強制しないため、CT未登録の証明書を受け入れるクライアントは、より大きなリスクがあります。

トラストストアをオフラインで確認する場合、chains.zipには検証用の証明書チェーン、追加テストケース、OpenSSLでの検証手順が含まれています。

原因について判明していること

中間証明書の秘密鍵は、認証局によって誤った方法で生成されました。そのため、誰でも証明書から秘密鍵を復元できます。

この復元は、証明書が作成された2025年4月以降可能だったと考えられます。その期間、これらの中間証明書はCertificate Transparencyログに記録されていません。したがって、Firefox、Chrome、Edge、SafariなどCTを必須とするクライアントは攻撃対象にならなかったと考えられます。

一方、ブラウザー以外の多くのクライアントはCertificate Transparencyを強制しません。攻撃者がこの鍵生成上の欠陥を悪用して、これらのクライアントを攻撃したかどうかは判明していません。

原因に関する技術的な詳細は、Mozillaのバグトラッカーにある初期インシデント報告に記載されています。

未修正のクライアント

チェッカーの背後にあるサーバーは、各User-Agentが接続に成功した回数、つまり侵害された中間CAをまだ信頼している回数だけを記録します。記録されるのはこの集計値のみです。

JA4フィンガープリントごとの件数を含む、より詳細なJSONデータも公開されています。

侵害された中間CA

impacted-intermediates.jsonには8件の中間CAとSectigoによるクロス署名が、roots.jsonにはそれらが接続するルート証明書が記載されています。

トラストストア運用者が実施できる対応

Mozillaのdev-security-policyフォーラムにあるスレッドを参照してください。

実装者向けには、変更が有効か検証する追加テストケースを含むchains.zipも役立ちます。

利用者が実施できる対応

利用者は、ブラウザーとOSをできるだけ早く最新バージョンへ更新してください。

修正版が提供されるまでの回避策

macOSのcurl、git、Python

macOSでは、Appleのネットワークおよびセキュリティフレームワークを使用するアプリケーションについて、侵害された中間CAがブロックされています。一方、組み込みのコマンドラインツールは、失効確認を行わずに/etc/ssl/cert.pemを使用して証明書を検証します。Appleは、今後のmacOSアップデートでこのファイルを更新すると案内しています。それまでは、影響を受けるルート証明書を利用者自身で削除できます。

ファイルをバックアップします。

[ -e /etc/ssl/cert.pem.orig ] || sudo cp -p /etc/ssl/cert.pem /etc/ssl/cert.pem.orig

emSign ECC Root CA - G3を削除します。

t=$(mktemp) &&
awk -v s='=== /C=IN/OU=emSign PKI/O=eMudhra Technologies Limited/CN=emSign ECC Root CA - G3' \
  '/^(===|###) /{skip=0} $0==s{skip=1} !skip' /etc/ssl/cert.pem > "$t" &&
[ -s "$t" ] && sudo install -m 0644 -o root -g wheel "$t" /etc/ssl/cert.pem; rm -f "$t"

成功した場合は何も表示されません。削除された内容を確認するには、次を実行します。

diff -u /etc/ssl/cert.pem.orig /etc/ssl/cert.pem

この操作だけでは、AAA Certificate ServicesへチェーンするSectigoのクロス署名付き中間CA 6件はブロックされません。これらもブロックする場合は、そのルート証明書も削除します。ただし、AAA Certificate Servicesへチェーンする影響を受けていないWebサイトの検証に失敗する可能性があります。

t=$(mktemp) &&
awk -v s='=== /C=GB/ST=Greater Manchester/L=Salford/O=Comodo CA Limited/CN=AAA Certificate Services' \
  '/^(===|###) /{skip=0} $0==s{skip=1} !skip' /etc/ssl/cert.pem > "$t" &&
[ -s "$t" ] && sudo install -m 0644 -o root -g wheel "$t" /etc/ssl/cert.pem; rm -f "$t"

結果を確認します。どちらかのルート証明書がファイルに残っていれば表示され、両方とも削除されていれば何も表示されません。エラーが表示された場合は、バックアップから復元してください。

openssl crl2pkcs7 -nocrl -certfile /etc/ssl/cert.pem | openssl pkcs7 -print_certs -noout |
  grep -E 'emSign ECC Root CA - G3|AAA Certificate Services'

Appleは、公式の修正が提供されるまで、macOSアップデートによって/etc/ssl/cert.pemが置き換わる可能性があると注意喚起しています。アップデートのたびに、この手順を再実行する必要がある場合があります。

組み込みのpip3と、組み込みのpython3から作成した仮想環境内のpipは、別途、古いルート証明書のコピーを使用します。修正済みのシステムファイルを使用させるには、次を実行します。

F="$(/usr/bin/python3 -c 'import sysconfig; print(sysconfig.get_path("stdlib"))')/sitecustomize.py" &&
echo 'import os; os.environ.setdefault("PIP_CERT", "/etc/ssl/cert.pem")' | sudo tee -a "$F" > /dev/null &&
sudo chmod 644 "$F"

nix-darwinを使用している場合は、併せてNixOS向けの手順も実施してください。

詳しくは、Appleの公式案内を参照してください。

Linux

ディストリビューションから更新済みのca-certificatesパッケージが提供されるまで、十分な知識がある利用者は、システムトラストストアで影響を受けるルート証明書を信頼しないよう設定できます。一般利用者には推奨しません。

DebianおよびUbuntuではrootで実行します。

sed -i \
  -e 's|^mozilla/emSign_ECC_Root_CA_-_G3.crt|!&|' \
  -e 's|^mozilla/Comodo_AAA_Services_root.crt|!&|' \
  /etc/ca-certificates.conf && update-ca-certificates

DebianまたはUbuntuのパッケージ版OpenJDKを使用している場合、ca-certificates-javaの長年未解決の不具合により、システムトラストストアを変更してもJavaキーストア/etc/ssl/certs/java/cacertsは更新されません。これは、前述の回避策と更新済みca-certificatesパッケージの両方に該当します。OpenJDKの案内に従い、rootでキーストアを削除して再作成します。

rm -f /etc/ssl/certs/java/cacerts && update-ca-certificates --fresh

Alpineではrootで実行します。

apk add ca-certificates &&
sed -i -e 's|^mozilla/emSign_ECC_Root_CA_-_G3.crt|!&|' \
  /etc/ca-certificates.conf && update-ca-certificates

Fedora、RHEL、CentOS Stream、Rocky Linux、AlmaLinux、Amazon Linux 2023ではrootで実行します。

d=/etc/pki/ca-trust/source/blocklist; [ -d $d ] || d=/etc/pki/ca-trust/source/blacklist
trust extract --overwrite --format=pem-bundle \
  --filter='pkcs11:object=Comodo%20AAA%20Services%20root;type=cert' \
  $d/Comodo_AAA_Services_root.pem &&
trust extract --overwrite --format=pem-bundle \
  --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \
  $d/emSign_ECC_Root_CA_-_G3.pem &&
update-ca-trust

openSUSEおよびSLESではrootで実行します。

d=/etc/pki/trust/blocklist; [ -d $d ] || d=/etc/pki/trust/blacklist
trust extract --format=pem-bundle \
  --filter='pkcs11:object=Comodo%20AAA%20Services%20root;type=cert' \
  $d/Comodo_AAA_Services_root.pem &&
trust extract --format=pem-bundle \
  --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \
  $d/emSign_ECC_Root_CA_-_G3.pem &&
update-ca-certificates

Arch Linuxではrootで実行します。

trust extract --format=pem-bundle \
  --filter='pkcs11:object=emSign%20ECC%20Root%20CA%20-%20G3;type=cert' \
  /etc/ca-certificates/trust-source/blocklist/emSign_ECC_Root_CA_-_G3.pem &&
update-ca-trust

NixOSでは設定へ次を追加します。

security.pki.caCertificateBlacklist = [
  "Comodo AAA Services root"
  "emSign ECC Root CA - G3"
];

Windows

Microsoftは、Windowsの証明書信頼リストの自動更新を通じて、対象証明書のブロックを配布しています。この更新を受信している端末では、以下の回避策は不要です。オフライン端末や自動更新を無効化した端末など、更新を受信できない端末では、このスクリプトを使用して管理者が侵害された証明書をローカルでブロックできます。

この対策は企業管理下の端末には推奨しません。展開は組織のIT部門が管理するため、ローカルで変更を適用する前に担当部署へ確認してください。

フッターからリンクしているGitHubリポジトリでBlock-EmudhraCompromisedCA.ps1をダウンロードして内容を確認し、管理者権限のPowerShellターミナルから実行してください。PowerShell 5.1以降と、Windows標準のPKIモジュールが必要です。このコマンドが実行ポリシーを回避するのは現在のプロセスだけであり、端末全体のポリシーは変更しません。組織によって強制されたポリシーでは、実行できない場合があります。

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Block-EmudhraCompromisedCA.ps1

このスクリプトは、侵害された中間CAとクロス署名証明書の計16件を、LocalMachine\Disallowed（信頼されていない証明書）へ登録します。

この対策は、Windowsの証明書トラストストアとチェーン検証を使用するクライアント（Schannel TLSおよびAuthenticodeを含む）に適用されます。「信頼されたルート証明機関」を変更せず、「信頼されていない証明書」へブロック対象を追加します。独自のCAバンドルを使用するアプリケーションには、引き続き個別の更新が必要です。

Android

多くのAndroid端末には、Google Play開発者サービスの更新経路を通じて、対象証明書をブロックする更新が自動配信されています。

更新済みブロックリストをまだ受信していない端末では、システムトラストストアで影響を受けるルート証明書を無効化できる場合があります。「設定」を開き、「信頼できる認証情報」を検索してください。通常は「セキュリティ」から「暗号化と認証情報」の中にあります。「システム」タブで次の各証明書を選び、「無効にする」を選択します。

  • emSign ECC Root CA - G3（eMudhra Technologies Limitedに表示）
  • AAA Certificate Services（Comodo CA Limitedに表示）

一覧にあるその他のeMudhraおよびComodoの証明書は影響を受けていないため、有効のままにしてください。AAA Certificate Servicesを無効にすると、現在もこのルートへチェーンする一部のWebサイトでエラーになる可能性があります。端末が更新を受信した後は、同じ画面からルート証明書を再び有効にできます。

Android端末によっては、システム組み込みルート証明書を利用者が無効化できない場合があります。

HarmonyOS 4.3以前を使用している場合は、他のAndroidベースのシステムと同じ方法で、システム組み込みルート証明書を無効化できます。

OpenHarmony

OpenHarmonyベースのHarmonyOSでは、利用者がシステム組み込みルートを無効化できません。修正版が提供されるまで、利用者側で実施できる回避策はありません。

NetBSD

NetBSD 10以降ではrootで実行します。

certctl untrust /usr/share/certs/mozilla/all/emSign_ECC_Root_CA_-_G3.pem &&
certctl untrust /usr/share/certs/mozilla/all/Comodo_AAA_Services_root.pem

FreeBSD

FreeBSD 14以降では次のコマンドをrootで実行します。

cp /etc/ssl/certs/14bc7599.0 /usr/share/certs/untrusted/14bc7599.pem
cp /etc/ssl/certs/ee64a828.0 /usr/share/certs/untrusted/ee64a828.pem
certctl rehash
